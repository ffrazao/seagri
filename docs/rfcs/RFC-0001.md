# RFC-0001 [1]

# Arquitetura Base — Plataforma Multi-Tenant de Gestão de Presença [1]

**Status:** Draft [1]
**Autor:** Equipe de Arquitetura [1]
**Data:** 2026-02-24 [1]
**Escopo:** Fundação arquitetural e decisões estruturais do MVP [1]

---

## 1. Contexto [1]

Este RFC define a fundação arquitetural da plataforma de gestão de presença multi-tenant com validação geográfica e biométrica [1].
O sistema deverá permitir que usuários autenticados criem ambientes organizacionais para registrar, validar e auditar presença de terceiros [1].

Aplicabilidade [2]:
* B2B [2]
* B2G [2]
* Educação [2]
* Eventos [2]
* Projetos [2]
* Uso cidadão [2]

Foco desta fase: **Arquitetura estrutural correta e evolutiva.** [2]

Explicitamente fora de escopo neste momento [2]:
* Regras trabalhistas [2]
* Banco de horas [2]
* Cálculos de jornada [2]
* Escalas [2]

---

## 2. Objetivos [2]

1. Definir arquitetura técnica do MVP [2]
2. Garantir base multi-tenant segura [2]
3. Estabelecer separação clara entre identidade e domínio [2]
4. Preparar estrutura para biometria e antifraude [2]
5. Minimizar retrabalho estrutural futuro [2]
6. Operar exclusivamente com tecnologias open source no MVP [3]

---

## 3. Requisitos Funcionais do MVP [3]

O MVP deve permitir [3]:
* Autenticação via Keycloak [3]
* Criação de entidade organizacional [3]
* Associação de usuários via código de convite [3]
* Registro de presença [3]
* Captura de geolocalização [3]
* Captura de imagem facial [3]
* Armazenamento de evidência [3]
* Vínculo do registro com entidade e unidade física [3]

---

## 4. Requisitos Não Funcionais [3]

* Multi-tenancy com isolamento lógico [3]
* Auditoria rastreável [3]
* Execução via Docker [3]
* Stack open source [4]
* Arquitetura evolutiva [4]
* Baixo acoplamento entre identidade e domínio [4]

## 7. Estratégia de Multi-Tenancy [6]

### 7.1 Decisão para MVP [6]
* Banco único [6]
* Schema único [6]
* Isolamento por organization_id [6]
* Todas queries obrigatoriamente filtradas por organization_id [6]

Justificativa [6]:
* Reduz complexidade inicial [6]
* Mantém evolutividade [6]
* Permite futura migração para schema por tenant [6]

### 7.2 Evolução Futura [6]
Possibilidade de:
* Schema por tenant [6]
* Banco por tenant (clientes enterprise) [6]
* Realm dedicado no Keycloak para clientes pagos [6]

---

## 8. Estratégia de IAM (Keycloak) [6]

### 8.1 Realm [7]
Decisão MVP: Realm único [7]

### 8.2 Clients [7]
* Backend: confidential client [7]
* Web SPA: public client [7]
* Mobile: public client com PKCE [7]

### 8.3 Roles [7]
Separação:
* Realm roles → permissões globais [7]
* Client roles → não priorizar no MVP [7]
* Roles de domínio → armazenadas na tabela Membership [7]

Motivo: Evitar acoplamento entre estrutura organizacional e Keycloak [7].

### 8.4 Claims [7]
Incluir no token apenas [7]:
* sub [7]
* email [7]
* preferred_username [7]

Tenant NÃO deve estar fixo no token [7]. O contexto organizacional deve ser resolvido por request [7].

### 8.5 Integração com Active Directory / LDAP (Bootstrap) [8]
Conforme definido na RFC-0007, a integração com o Active Directory/LDAP operará em modo Stateless [8].
* O parâmetro `Import Users` do Keycloak ficará sempre em `Off` [8]. O LDAP atua apenas como autenticador em tempo real, garantindo o corte de acesso imediato em caso de desligamento do servidor [8].
* O LDAP atua como um mecanismo facilitador de *Bootstrap* (carga inicial) para preenchimento estrutural (árvore de OUs) no momento da criação do Tenant [8].
* A autorização de domínio reside exclusivamente na aplicação [9]. Após a importação inicial, as modificações na estrutura de setores, lotações e identificação de gestores passam a viver e ser alteradas exclusivamente no banco de dados da plataforma (PostgreSQL), garantindo independência da equipe de TI do órgão [9].

## 9. Arquitetura da Aplicação [9]

### 9.1 Decisão [9]
Monolito modular [9].

Justificativa [9]:
* Baixo overhead operacional [9]
* Facilidade de refatoração [9]
* Boundary interno claro [9]
* Pronto para futura extração de serviços [9]

Estrutura sugerida [10]:
```text
core-domain
organization-module
attendance-module
biometric-module
audit-module
infrastructure

--------------------------------------------------------------------------------
10. Geolocalização
Decisões:
Validação sempre no backend
Comparação contra geofence persistido
Registrar precisão do GPS
Nunca confiar apenas em validação do client
Mitigações básicas MVP:
Rejeitar precisão acima de limite configurável
Detectar inconsistências grosseiras (saltos impossíveis)
Risco aceitável no MVP: Spoofing sofisticado.
Risco não aceitável: Validação puramente client-side.

--------------------------------------------------------------------------------
11. Biometria
11.1 MVP (Open Source)
Processamento no backend
Uso de biblioteca open source (ex: OpenCV + modelo facial)
Armazenar template biométrico, não apenas imagem bruta
11.2 Armazenamento
Imagens em object storage local (MinIO)
Criptografia em repouso
Referência via UUID
11.3 Riscos
Aceitável no MVP:
Precisão biométrica moderada
Ausência de prova de vida avançada
Não aceitável:
Armazenamento de imagem sem criptografia
Templates biométricos sem proteção

--------------------------------------------------------------------------------
12. Registro Colaborativo (Preparação Estrutural)
Mesmo sem implementar kiosk agora: AttendanceRecord deve conter:
device_id
registration_mode (SELF | SHARED_DEVICE)
intermediary_user_id (nullable)
Permite auditoria futura sem refatoração estrutural.

--------------------------------------------------------------------------------
13. Auditoria
Desde o MVP:
Tabela audit_log
Armazenar: actor, action, entity_type, entity_id, timestamp, ip, user_agent.
Nunca sobrescrever registros de presença.

--------------------------------------------------------------------------------
14. Segurança desde o Primeiro Commit
HTTPS obrigatório
CORS restritivo
Validação server-side obrigatória
Sanitização de entrada
Criptografia em repouso
Segregação de responsabilidades entre módulos

--------------------------------------------------------------------------------
15. Fluxo de Registro de Presença
Usuário autentica via Keycloak
Mobile/Web obtém token
Captura: Localização, Precisão, Imagem facial
Envia para backend
Backend: Valida token, Resolve organização, Valida geofence, Executa comparação biométrica, Persiste registro, Gera log de auditoria.

--------------------------------------------------------------------------------
16. Principais Riscos Estruturais
Acoplamento excessivo ao Keycloak
Misturar tenant no token
Falta de separação entre domínio e infraestrutura
Ignorar auditoria desde início
Overengineering com microsserviços prematuros

--------------------------------------------------------------------------------
17. Roadmap Técnico Inicial
Fase 1: Setup infraestrutura Docker, Configuração Keycloak, Estrutura base Spring Boot, Modelagem mínima de banco. Fase 2: Organização + convite, Membership, Registro simples de presença sem biometria. Fase 3: Integração biométrica básica, Geofence server-side, Auditoria estruturada. Fase 4: Hardening de segurança, Testes antifraude básicos.

--------------------------------------------------------------------------------
18. Decisão Estratégica Inicial
A primeira frente a iniciar deve ser: Backend.
Justificativa:
Define modelo de domínio
Define contrato de API
Define estrutura multi-tenant
Define segurança
Web e mobile devem ser consumidores de contrato estável

--------------------------------------------------------------------------------
19. Conclusão
Este RFC estabelece a base arquitetural mínima segura, auditável e evolutiva para o MVP da plataforma.
Qualquer decisão futura deve:
Preservar isolamento multi-tenant
Manter separação entre identidade e domínio
Evitar dependências estruturais não substituíveis
Priorizar auditabilidade
