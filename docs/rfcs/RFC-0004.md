# RFC-0004

# Estratégia de Evolução para Clientes Enterprise

## (Isolamento Forte, Compliance e Hardening)

**Status:** Draft
**Autor:** Arquitetura
**Data:** 2026-02-24
**Depende de:** RFC-0001, RFC-0002, RFC-0003

---

# 1. Contexto

O MVP foi projetado com:
* Banco único
* Schema único
* Realm único no Keycloak
* Isolamento lógico por `organization_id`

Esse modelo é adequado para:
* Early stage
* Clientes pequenos/médios
* Baixo risco regulatório

Entretanto, clientes enterprise (especialmente B2G e grandes empresas) exigirão:
* Isolamento mais forte
* Garantias formais de compliance
* Governança de dados
* SLAs
* Hardening de segurança
* Controle de residência de dados

Este RFC define a evolução arquitetural necessária.

---

# 2. Objetivos

1. Permitir múltiplos níveis de isolamento
2. Atender requisitos regulatórios (ex: LGPD)
3. Permitir customizações enterprise sem fork de código
4. Garantir escalabilidade horizontal
5. Minimizar impacto arquitetural no core

---

# 3. Modelo de Segmentação de Clientes

Definir três níveis:

## Tier 1 — Shared (MVP)
* Banco compartilhado
* Schema único
* Realm único
* Isolamento lógico

## Tier 2 — Isolamento Intermediário
* Schema por tenant
* Realm dedicado opcional
* Recursos segregados

## Tier 3 — Enterprise Dedicated
* Banco dedicado
* Infra dedicada
* Realm exclusivo
* Criptografia dedicada
* Ambiente isolado

WAF na borda

Rotação periódica de chaves
Auditoria imutável externa (opcional)

7.2 Criptografia

Exportação para SIEM

tenant_id como label obrigatório em logs

--------------------------------------------------------------------------------
9. Escalabilidade
9.1 Aplicação
Stateless
Horizontal scaling
Sessionless (JWT-based)
9.2 Banco
Read replicas
Particionamento por tenant
Estratégia de archiving

--------------------------------------------------------------------------------
10. Customizações Enterprise
Não permitir:
Fork de código por cliente
Permitir:
Feature flags por tenant
Configuração de policy por organização
Parametrização antifraude
SLA diferenciado
Estrutura: Tabela tenant_configuration:
organization_id
feature_flags
risk_threshold
geofence_policy
biometric_threshold

--------------------------------------------------------------------------------
11. Isolamento de Storage
MVP:
Bucket único (ex: MinIO)
Enterprise:
Bucket por tenant
Criptografia dedicada
Política de retenção customizada

--------------------------------------------------------------------------------
12. Auditoria Avançada
Enterprise pode exigir:
Log imutável externo
Exportação automática
Trilha de decisão de autorização
Versionamento de policies
Preparar estrutura para:
policy_version
risk_model_version

--------------------------------------------------------------------------------
13. Riscos de Escalar Sem Arquitetura Preparada
Migração dolorosa de banco único
Dependência forte de realm único
Criptografia global impossível de separar
Dificuldade de exportar dados por tenant

--------------------------------------------------------------------------------
14. Estratégia de Evolução Recomendada
MVP com isolamento lógico
Introduzir TenantResolver abstrato desde o início
Encapsular acesso a banco via camada multi-tenant
Não acoplar domínio ao modelo físico do banco
Manter feature flags por organização

--------------------------------------------------------------------------------
15. Critérios para Migrar Cliente para Tier Superior
Volume de dados elevado
Exigência contratual
Auditoria externa obrigatória
Requisito de residência de dados
Exigência de SLA dedicado

--------------------------------------------------------------------------------
16. Decisão Estratégica
A arquitetura deve nascer:
Multi-tenant aware
Storage-agnostic
Realm-agnostic
Database-topology-agnostic
Isso garante:
Evolução para enterprise sem refatoração estrutural
Separação clara entre core e infraestrutura
Possibilidade de oferecer planos diferenciados

--------------------------------------------------------------------------------
17. Conclusão
O MVP deve ser simples, mas estruturalmente preparado para:
Isolamento físico
Compliance rigoroso
Hardening de segurança
Operação enterprise
A decisão central é: Preparar abstrações agora para evitar migração estrutural traumática no futuro.
