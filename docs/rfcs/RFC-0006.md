# RFC-0006

## Arquitetura de Autorização Granular e Controle de Acesso Dinâmico

**Status:** Draft
**Autor:** Equipe de Arquitetura
**Data:** 24/02/2026
**Versão:** 1.1

---

## 1. Objetivo

Definir a arquitetura de autorização **extremamente granular**, permitindo:

* Controle por **endpoint + método HTTP**
* Controle por **atributos do recurso (field-level security)**
* Controle por **usuário individual (ABAC / PBAC)**
* Governança centralizada e auditável
* Total autonomia de domínio (isolamento do Keycloak)

Este RFC complementa o modelo básico RBAC definido anteriormente (RFC-0002), introduzindo um modelo híbrido RBAC + ABAC + Policies Dinâmicas gerido inteiramente pela aplicação.

---

## 2. Problema

O modelo tradicional baseado apenas em roles (RBAC) genéricas:

* Não permite variações finas por usuário
* Não controla campos específicos na resposta
* Não diferencia permissões por contexto (horário, local, unidade, vínculo)

Para o sistema de registro de presença automática, é necessário:

* Restringir visualização de dados por unidade organizacional
* Permitir exceções individuais
* Controlar operações por endpoint/método
* Filtrar campos da resposta dinamicamente

---

## 3. Requisitos

### 3.1 Funcionais

1. Autorização por endpoint, método HTTP, atributos do recurso, usuário e unidade.
2. Suporte a políticas contextuais (horário, geolocalização).
3. Resposta parcialmente filtrada.
4. Auditoria completa de decisões.

### 3.2 Não Funcionais

* Baixa latência (< 20ms por decisão)
* Cache distribuído para autorização local
* Alta auditabilidade

---

## 4. Modelo de Autorização Proposto

### 4.1 Camadas de Controle

A arquitetura formaliza a remoção de acoplamento do Keycloak para autorização. Toda decisão ocorre no banco do sistema (PostgreSQL).

| Camada | Tipo | Tecnologia |
| -------------------------- | ------------------ | ------------------------------- |
| Autenticação (Identidade) | OIDC | Keycloak |
| Autorização coarse-grained | RBAC | Tabela `membership` (PostgreSQL)|
| Autorização fine-grained | ABAC / PBAC | Policy Engine Interno (PDP custom) e Tabela `user_permissions_override` |
| Field-level filtering | Middleware interno | API Gateway / Interceptors |

---

## 5. Modelo Híbrido

### 5.1 RBAC (Base)

Roles armazenadas na tabela interna `membership` definem permissões amplas no contexto de uma Organização:

* ROLE_ADMIN
* ROLE_GESTOR
* ROLE_SERVIDOR

### 5.2 ABAC (Atributos)

A Policy Engine avalia atributos em tempo real (dados internos do domínio):

* user.id
* user.unidade
* recurso.unidade
* horario
* localização

### 5.3 PBAC (Policy-Based)

Políticas explícitas gravadas no banco na coluna JSONB:

```json
{
  "policy": "usuario_somente_sua_unidade",
  "effect": "permit",
  "condition": "user.unidade == resource.unidade"
}

--------------------------------------------------------------------------------
6. Arquitetura Técnica
6.1 Fluxo
Cliente autentica no Keycloak.
Recebe JWT apenas com identificação básica (ex: sub, email).
API recebe requisição.
Middleware de Autorização intercepta e extrai o ID da requisição e do locatário (Tenant/Organização).
O Policy Decision Point (PDP) customizado da aplicação é invocado.
O PDP consulta o cache/PostgreSQL (membership e user_permissions_override).
API:
Permite
Nega
Permite com filtro de campos

--------------------------------------------------------------------------------
7. Uso do Motor de Autorização Interno (PDP Customizado)
Ao invés de delegar ao Authorization Services do Keycloak, a aplicação resolve suas permissões mapeando recursos internamente.
7.1 Recursos Modelados
Exemplo:
Recurso: /presencas
Scopes: view, edit, delete, approve

--------------------------------------------------------------------------------
8. Controle por Endpoint + Método
Mapeamento interno da aplicação:
Endpoint
Método
Scope
/presencas
GET
view
/presencas
POST
create
/presencas/{id}
PUT
edit
/presencas/{id}
DELETE
delete
O Middleware traduz a requisição HTTP para o respectivo scope de autorização.

--------------------------------------------------------------------------------
9. Controle por Campo (Field-Level Security)
Após decisão positiva:
A política local retorna lista de campos permitidos.
O Middleware serializa apenas o filtro JSON aprovado.
Exemplo de retorno de política:
{
  "allowedFields": [
    "nome",
    "matricula",
    "statusPresenca"
  ]
}
Campos sensíveis (CPF, registro bruto) são removidos dinamicamente da resposta para perfis não autorizados.

--------------------------------------------------------------------------------
10. Controle por Usuário Individual (Exceções)
Implementação:
Para permitir exceções sem alterar a role global do usuário (ex: um SERVIDOR que atua temporariamente como aprovador), a engine avalia a tabela user_permissions_override.
SELECT * FROM user_permissions_override
WHERE user_id = ? AND resource = '/presencas' AND scope = 'approve';
Isso garante granularidade extrema mantendo o isolamento do Keycloak.

--------------------------------------------------------------------------------
11. Contextualização por Geolocalização
A política interna pode validar regras híbridas no momento do request:
if (request.ip() in allowedRange)
if (user.currentLocation() within unidade.geofence())
Isso permite:
Aprovação apenas dentro da rede do governo.
Bloqueio remoto fora do horário.

--------------------------------------------------------------------------------
12. Auditoria
Toda decisão de PDP deve registrar no audit_log:
userId
recurso
método
decisão
políticas aplicadas
timestamp
Logs devem ser imutáveis.

--------------------------------------------------------------------------------
13. Estratégia de Performance
13.1 Cache
Como a consulta ao PostgreSQL ocorrerá por request, é obrigatório o uso de cache distribuído (ex: Redis).
Chave de cache: userId + organizationId + resource + scope
TTL curto (30–60s) para garantir revogação rápida.

--------------------------------------------------------------------------------
14. Modelo de Banco (Permissões Dinâmicas)
Conforme a RFC-0005, a tabela que sustenta essa arquitetura é a user_permissions_override, contendo o campo condition_json para suportar regras lógicas de ABAC puramente no banco de dados.

--------------------------------------------------------------------------------
15. Segurança
Nunca confiar apenas no frontend.
Sempre validar no backend.
JWT deve ser validado criptograficamente com RS256.

--------------------------------------------------------------------------------
16. Conclusão
A arquitetura proposta permite autorização por endpoint, método, campo, usuário específico e contexto sem depender dos serviços de autorização complexos do Keycloak.
Centralizar as regras no banco de dados (PostgreSQL) sob o domínio da aplicação elimina o acoplamento excessivo e viabiliza a autonomia do negócio.
