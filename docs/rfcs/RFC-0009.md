# RFC-0009

# Implementação da Camada Web / REST Endpoints

**Status:** Draft [1]
**Sistema:** API de Serviços SEAGRI-DF [1]
**Plataforma:** Spring/Java [1]
**Segurança:** Keycloak [1]
**Banco de dados:** PostgreSQL [1]
**Modelo:** Multitenant [1]

---

## 1. Objetivo

Definir os padrões técnicos para implementação da camada Web (REST Controllers) da aplicação [1].

Essa camada será responsável por:
* Expor endpoints HTTP [1].
* Validar requisições [1].
* Delegar chamadas para a camada de aplicação [1].
* Padronizar respostas da API [1].
* Integrar segurança, logging e auditoria [1].

A implementação deve respeitar as decisões arquiteturais já definidas nas RFCs anteriores:
* DDD (Domain-Driven Design) [2].
* Arquitetura Hexagonal (Ports & Adapters) [2].
* Separação clara entre domínio, aplicação e infraestrutura [2].

A camada Web deve permanecer fina, contendo apenas responsabilidades de interface [2].

---

## 2. Contexto do Sistema

A API está sendo desenvolvida para o órgão público SEAGRI-DF e possui as seguintes características:
* Autenticação via Keycloak [2].
* Modelo multitenant [2].
* Persistência em PostgreSQL [2].
* Exposição de serviços via REST API [3].

A camada Web deve receber requisições externas, validar dados e delegar a execução aos Application Services [3]. Regras de negócio não devem ser implementadas nos controllers [3].

---

## 3. Estrutura da Camada Web

A camada Web utilizará uma estrutura baseada em controllers reutilizáveis, permitindo padronização e redução drástica de duplicação de código [3].

---

## 4. Controller Base da API

Será criado um controller base genérico, responsável pelos comportamentos comuns a toda a camada Web [3].

**Componente:** `AbstractApiController` [4]

Esse controller não assume operações CRUD e oferecerá funcionalidades como:
* Extração do identificador do usuário autenticado (Keycloak `sub`) [4].
* Acesso ao identificador do tenant atual repassado via requisição [4].
* Utilitários para construção do envelopamento padronizado de respostas (`ApiResponse`) [4].
* Integração com logging estruturado e suporte à auditoria [4].

Todos os controllers da aplicação estenderão direta ou indiretamente este componente [4].

---

## 5. Controllers Especializados para CRUD (Dupla Hierarquia)

Para entidades que expõem operações padrão de persistência, utilizaremos uma dupla hierarquia de controllers genéricos, alinhada à nossa camada de serviços, respeitando o isolamento do modelo Multitenant [4].

### 5.1. Contexto Global (Sem Tenant)
Para tabelas de apoio e domínios globais (ex: Localidades, Unidades de Medida).

**Componente:** `AbstractCrudController<DOMAIN, ID, REQUEST_DTO, RESPONSE_DTO, SERVICE>` [5]

### 5.2. Contexto Isolado (Multi-Tenant)
Para as entidades exclusivas de cada organização. Este controller injetará compulsoriamente a validação de segurança.

**Componente:** `AbstractCrudTenantController<DOMAIN, ID, REQUEST_DTO, RESPONSE_DTO, SERVICE>`

Ambos os controllers deverão:
* Expor endpoints CRUD padrão (GET, POST, PUT/PATCH, DELETE) [5].
* Delegar operações aos respectivos Application Services (`CrudSrv` ou `CrudTenantSrv`) [5].
* Forçar a passagem do `organizacaoId` em todas as rotas do contexto isolado.

---

## 6. Tratamento de Entidades Imutáveis (Comando Único)

Em conformidade com as restrições arquiteturais da RFC-0005 e da RFC-008 (Comando Único e Imutabilidade), entidades estritamente imutáveis **jamais deverão estender os controllers genéricos de CRUD** [6].

**Exemplo:** `RegistroPresencaController`

Estes controllers deverão estender diretamente o `AbstractApiController` [6], expondo **exclusivamente**:
* Rotas de `POST` (para recepção do evento bruto do dispositivo).
* Rotas de `GET` (para listagem de histórico e relatórios).

Sob nenhuma hipótese rotas de `PUT` ou `DELETE` serão expostas para essas entidades.

---

## 7. Consultas Simplificadas (Lookup para UI)

O sistema precisará alimentar componentes de interface de usuário (UI) como `select`, `combobox` e `autocomplete` através de listas simplificadas e não paginadas [7].

Ao invés de criar controllers apartados para isso, os controllers abstratos de CRUD (`AbstractCrudController` e `AbstractCrudTenantController`) deverão expor um endpoint específico de lookup nativamente.

**Exemplo de rota embutida:**
`GET /api/v1/organizacoes/{orgId}/unidades/lookup`

Esse endpoint retornará a coleção completa (não paginada) dos dados, utilizando os métodos `buscarTudo()` previamente definidos na camada de aplicação [12].

---

## 8. Padronização de Respostas da API

Todas as respostas HTTP devem seguir um formato consistente através da criação de um wrapper padrão de resposta [8].

**Componente:** `ApiResponse<T>` [8]

**Campos obrigatórios:**
* `timestamp` [8]
* `status` (Código HTTP) [8]
* `message` [8]
* `payload` (Os dados de retorno) [8]
* `errors` (Lista de validações, se houver) [8]

Esse padrão deve ser compatível com o mecanismo global de tratamento de exceções [8].

---

## 9. Tratamento Global de Exceções

A API possuirá um tratamento centralizado de erros através de `@ControllerAdvice` e `@ExceptionHandler` [8].

O *Global Exception Handler* deverá interceptar e envelopar dentro do formato `ApiResponse` as seguintes classificações de erro [9]:
* Erros de validação (DTOs inválidos) [9].
* Erros de regra de negócio (ex: violação de unicidade) [9].
* Erros de segurança (ex: violação de Tenant) [9].
* Erros técnicos do sistema [9].

---

## 10. Validação Automática de Requisições

As requisições utilizarão validação declarativa baseada nas anotações do *Jakarta Validation* (ex: `@Valid`, `@NotNull`, `@NotBlank`) [9].
Isso garante a integridade dos dados, reduz as validações manuais nos controllers e padroniza a coleta de erros, que serão devolvidos pelo handler global [9].

---

## 11. Documentação e Versionamento

* **OpenAPI (Swagger):** A API terá documentação gerada automaticamente, descrevendo endpoints, formatos de DTO e permitindo testes interativos [10].
* **Versionamento:** Todos os endpoints utilizarão versionamento semântico nas URLs (ex: `/api/v1/...`) para garantir retrocompatibilidade futura [10].

---

## 12. DTO e Mapeamento

A API consumirá e retornará exclusivamente DTOs (Data Transfer Objects), nunca expondo as entidades do domínio diretamente [11].
O mapeamento entre DTOs e Entidades será automatizado, recomendando-se o uso do framework **MapStruct** devido à sua simplicidade, performance baseada em compilação e facilidade de manutenção [11].

---

## 13. Estrutura Conceitual Final da Camada Web

A organização da herança dos controllers obedecerá à seguinte hierarquia [12, 13]:

```text
AbstractApiController (Base com Utilitários e ApiResponse)
 ├── AbstractCrudController (Tabelas GLOBAIS com rotas genéricas + /lookup)
 │    └── DomínioGlobalCrudController
 │
 ├── AbstractCrudTenantController (Tabelas MULTI-TENANT com rotas genéricas + /lookup)
 │    ├── UnidadeController
 │    └── VinculoUsuarioController
 │
 └── Controllers Diretos (Regras Específicas, Imutáveis e Workflows)
      ├── RegistroPresencaController (Apenas GET e POST do comando único)
      ├── AutenticacaoController
      └── RelatoriosController
