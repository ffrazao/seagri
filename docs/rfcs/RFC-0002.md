# RFC-0002

# Modelo de Autorização Evolutivo — RBAC + ABAC com Extensão para ReBAC

**Status:** Draft
**Autor:** Arquitetura
**Data:** 2026-02-24
**Depende de:** RFC-0001

---

# 1. Contexto

O sistema é multi-tenant, com usuários podendo pertencer a múltiplas organizações simultaneamente.

A autorização não pode depender exclusivamente de roles do provedor de identidade.

Objetivo:
Estabelecer um modelo de autorização:
* Desacoplado do IdP
* Multi-tenant aware
* Evolutivo
* Auditável
* Compatível com cenários B2B e B2G

---

# 2. Princípios Arquiteturais

1. Autenticação ≠ Autorização
2. Autorização resolvida no domínio
3. Sempre contextual por organização
4. Negação por padrão (deny-by-default)
5. Policy evaluation determinística
6. Log de decisão obrigatório

---

# 3. Modelo Híbrido Proposto

## 3.1 Camadas

**Camada 1 — RBAC (base estrutural)**
Define papéis organizacionais.

**Camada 2 — ABAC (controle fino)**
Define regras baseadas em atributos.

**Camada 3 — ReBAC (futuro)**
Permite autorizações baseadas em relacionamentos complexos.

---

# 4. RBAC (Organizational Role-Based Access Control)

## 4.1 Papéis Base no MVP

* OWNER
* ADMIN
* MANAGER
* PARTICIPANT
* AUDITOR (preparação futura)

Papéis são armazenados na tabela `membership`.
Não devem residir no IdP.

---

## 4.2 Escopo do Papel

Role sempre contextual:
(user_id, organization_id) → role

Nunca global.

---

# 5. ABAC (Attribute-Based Access Control)

Necessário para evitar explosão de roles.

## 5.1 Atributos Relevantes

### Subject (usuário)
* role
* membership_status
* biometric_enrolled
* device_trust_level

### Resource
* organization_id
* unit_id
* owner_id
* record_status

### Environment
* request_time
* ip_address
* device_id
* registration_mode

---

## 5.2 Exemplos de Policies

* Participante pode registrar presença apenas para si.
* Manager pode registrar para membros da mesma unidade.
* Registro só é válido se `gps_valid == true`.
* Acesso a relatórios apenas se role ∈ {OWNER, ADMIN}.

---

# 6. Estrutura Técnica da Autorização

## 6.1 Camada de Policy Engine Interna

Implementação recomendada:

Interface:
AuthorizationService.evaluate( subject, action, resource, environment ) -> Decision

Decision:
* PERMIT
* DENY
* PERMIT_WITH_CONDITIONS

---

## 6.2 Onde Executar

* Sempre no backend
* Antes da execução do caso de uso
* Dentro da camada de aplicação

---

# 7. Integração com Keycloak

Uso restrito a:
* Autenticação
* Emissão de token
* Identificação do usuário (sub)

Não usar:
* Role organizacional no token
* Tenant fixo no token

Evita:
* Token inflation
* Inconsistência organizacional
* Complexidade de sincronização

---

# 8. Multi-Tenant Enforcement

Toda policy deve validar:
resource.organization_id == membership.organization_id
Qualquer divergência → DENY.

---

# 9. Auditoria de Decisão

Toda decisão sensível deve gerar registro:
* user_id
* organization_id
* action
* resource_id
* decision
* timestamp
* rationale (opcional no MVP)

Isso prepara compliance futura.

---

# 10. Preparação para ReBAC

Cenários futuros:
* Delegação temporária
* Supervisor indireto
* Hierarquia entre unidades
* Substituição em férias

Estrutura necessária:
Tabela `relationship`:
* subject_id
* object_id
* relationship_type
* organization_id
* validity_period

**Nota Técnica sobre Integração LDAP (conforme RFC-0007):**
Este modelo estrutural de relacionamentos (ReBAC) substitui inteiramente a necessidade de sincronizar ou ler atributos de delegação temporária (como o `managedBy` em OUs) diretamente do Active Directory. A gestão de férias, substitutos com vigência e hierarquias departamentais detalhadas passa a ser uma responsabilidade exclusiva do domínio da aplicação (PostgreSQL), garantindo flexibilidade e removendo a dependência operacional da equipe de TI.

Policy engine poderá consultar relações.

---

# 11. Anti-Patterns a Evitar

* Hardcode de role em controller
* Switch-case espalhado
* Autorização apenas por role
* Regra de negócio misturada com decisão de acesso
* Depender de claim de tenant no token

---

# 12. Roadmap Evolutivo

### Fase 1 — MVP
* RBAC simples
* Verificação contextual por organization_id

### Fase 2
* Introdução de ABAC básico
* Policy centralizada

### Fase 3
* DSL simples para policies
* Externalização parcial de regras

### Fase 4
* ReBAC
* Possível integração com motor dedicado (ex: OPA)

---

# 13. Riscos

Aceitável no MVP:
* Policies implementadas em código
* ABAC limitado

Não aceitável:
* Autorização dependente apenas do frontend
* Falta de isolamento multi-tenant
* Decisões não auditáveis

---

# 14. Exemplo de Fluxo de Autorização (Registro de Presença)

1. Usuário autenticado
2. Backend extrai `sub`
3. Busca membership por organization_id
4. Monta contexto:
   * subject
   * resource
   * environment
5. AuthorizationService.evaluate()
6. Se PERMIT → continua
7. Se DENY → HTTP 403
8. Loga decisão

---

# 15. Decisão Final

Adotar modelo híbrido:
RBAC estruturante + ABAC contextual + base preparada para ReBAC.

Separação clara entre:
* Identidade (IdP)
* Associação organizacional
* Política de autorização
* Execução do caso de uso

Isso garante:
* Escalabilidade
* Flexibilidade
* Segurança
* Evolução sem ruptura estrutural
