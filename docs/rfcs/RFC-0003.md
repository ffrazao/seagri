# RFC-0003

# Arquitetura Antifraude e Validação de Integridade
## (Geolocalização + Biometria + Dispositivo)

**Status:** Draft
**Autor:** Arquitetura
**Data:** 2026-02-24
**Depende de:** RFC-0001, RFC-0002

---

# 1. Contexto

O sistema registra presença com base em:
* Geolocalização
* Biometria facial
* Identificação de dispositivo
* Contexto organizacional

Sem mecanismos antifraude, o sistema se torna vulnerável a:
* GPS spoofing
* Uso de foto estática
* Registro remoto indevido
* Compartilhamento indevido de credenciais
* Automação via scripts

Este RFC define mecanismos de mitigação para o MVP (open source, sem serviços pagos), com arquitetura evolutiva.

---

# 2. Princípios Antifraude

1. Nunca confiar exclusivamente no client
2. Toda validação crítica ocorre no backend
3. Registro deve ser auditável
4. Risco é reduzido, não eliminado
5. Defesa em camadas (defense-in-depth)

---

# 3. Modelo de Ameaças

## 3.1 GPS Spoofing
Usuário simula localização usando app falso ou mock location.

## 3.2 Face Replay
Usuário apresenta foto ou vídeo no lugar do rosto real.

## 3.3 Registro Remoto
Usuário fora do local registra presença via manipulação de payload.

## 3.4 Device Sharing Abusivo
Um usuário registra múltiplos outros indevidamente.

## 3.5 Manipulação de Timestamp
Tentativa de alterar horário do registro.

# 5. Geolocalização

## 5.1 Decisão Arquitetural
* Geofence armazenado no backend
* Cálculo de validação feito exclusivamente no backend
* Registrar:
  * latitude
  * longitude
  * precisão
  * timestamp client
  * timestamp servidor

Nunca confiar apenas no client.

---

6. Biometria Facial
6.1 Arquitetura MVP (Open Source)
Processamento no backend usando:
OpenCV
Modelo facial open source
Geração de template vetorial
Armazenar:
Template biométrico (embedding)
Referência da imagem capturada
Score de similaridade
Nunca armazenar apenas imagem bruta como validação.

--------------------------------------------------------------------------------
6.2 Fluxo de Validação
Usuário envia imagem
Backend:
Detecta face
Gera embedding
Compara com template cadastrado
Calcula similaridade
Se score ≥ threshold → válido
Registrar score no banco

--------------------------------------------------------------------------------
6.3 Mitigação de Replay
MVP:
Exigir captura em tempo real
Bloquear upload de imagem da galeria
Validar metadados básicos
Futuro:
Liveness detection
Desafio dinâmico (piscar, mover cabeça)

--------------------------------------------------------------------------------
6.4 Riscos Aceitáveis no MVP
Ausência de liveness avançado
Precisão moderada
Não aceitável:
Armazenar biometria sem criptografia
Não registrar score de similaridade

--------------------------------------------------------------------------------
7. Dispositivo
7.1 Device ID
Gerar UUID na primeira instalação. Persistir no app. Enviar em cada requisição.
Backend armazena:
device_id
first_seen
last_seen
platform
user_agent

--------------------------------------------------------------------------------
7.2 Trust Level
Calcular dinamicamente:
Dispositivo já utilizado antes?
Número de usuários associados?
Histórico consistente?
Campo:
device_trust_level = LOW | MEDIUM | HIGH

--------------------------------------------------------------------------------
7.3 Registro Colaborativo
AttendanceRecord deve conter:
registration_mode (SELF | SHARED_DEVICE)
intermediary_user_id (nullable)
Permite auditoria futura.

--------------------------------------------------------------------------------
8. Timestamp Seguro
Servidor deve registrar:
server_received_at = now()
Ignorar timestamp do client como verdade absoluta.
Se diferença excessiva:
Registrar flag de inconsistência

--------------------------------------------------------------------------------
9. Score de Risco Composto
Cada registro pode gerar:
risk_score = f(
  gps_valid,
  gps_accuracy,
  biometric_score,
  device_trust_level,
  velocity_check,
  mock_location_flag
)
No MVP:
Apenas registrar
Não bloquear automaticamente
Futuro:
Bloqueio automático
Revisão manual

--------------------------------------------------------------------------------
10. Auditoria Imutável
AttendanceRecord nunca deve ser alterado.
Se invalidado:
Criar novo registro de status
Nunca sobrescrever
Audit log deve registrar:
fatores de risco
score biométrico
decisão final

--------------------------------------------------------------------------------
14. Anti-Patterns
Validar GPS apenas no client
Aceitar imagem sem comparação
Não registrar score biométrico
Não guardar precisão GPS
Permitir update de AttendanceRecord

--------------------------------------------------------------------------------
15. Decisão Final
Adotar antifraude em camadas:
Geográfico
Biométrico
Dispositivo
Comportamental
Auditoria imutável
Objetivo no MVP: Reduzir fraude simples e preparar estrutura para antifraude avançado sem refatoração estrutural.
